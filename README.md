# Сервис управления фестивальными площадками

Репозиторий проекта: https://github.com/Mastertuz/festival-venue-service

## Назначение

Приложение для управления фестивальными площадками и их бронированием.
Консольная версия приложения (ПР3) дополнена веб-интерфейсом на Django (ПР5), который
в ПР6 переведён на систему шаблонов Django. В ПР7 данные были перенесены в базу SQLite и
получались SQL-запросами, а в ПР9 слой данных веб-интерфейса переведён на Django ORM
(в ПР10 настроена административная панель Django и доработаны модели):
таблицы описаны моделями Django, структура базы управляется миграциями, представления
получают данные через менеджеры моделей.

В браузере можно:

* просматривать список площадок, искать площадки по названию и отбирать по вместимости;
* просматривать информацию о конкретной площадке и её доступность на текущую дату;
* искать площадки, свободные на выбранную дату и подходящие по числу посетителей;
* просматривать список бронирований с поиском, фильтрами (дата, площадка, организатор,
  только активные), сортировкой и постраничным выводом;
* просматривать информацию о конкретном бронировании;
* просматривать статистику бронирований;
* видеть на главной странице число активных бронирований и ближайшие фестивали.

Консольная версия позволяет:

* просматривать площадки, искать их по названию, сортировать и фильтровать по вместимости;
* проверять соответствие вместимости площадки ожидаемому числу посетителей;
* проверять доступность площадки на дату проведения фестиваля;
* вести список организаторов и фестивалей;
* бронировать площадку под фестиваль;
* отменять бронирования;
* просматривать расписание бронирований;
* хранить данные между запусками приложения.

## Целевая аудитория

* организаторы фестивалей и культурных мероприятий;

## Предметная область

Основными объектами предметной области являются:

* площадка;
* организатор;
* фестиваль;
* бронирование (запись расписания).

Организатор проводит фестивали. Для фестиваля бронируется площадка на дату его проведения.
Одна площадка не может иметь два активных бронирования на одну и ту же дату.
Отменённое бронирование не блокирует площадку и позволяет создать новое бронирование
на эту дату.

## Основные сущности

### Venue — площадка

Объект `Venue` представляет площадку, доступную для проведения фестиваля.

Основные атрибуты:

* `id` — уникальный идентификатор площадки;
* `name` — название площадки;
* `capacity` — вместимость площадки.

Основные методы:

* `is_suitable_for()` — проверка соответствия вместимости ожидаемому числу посетителей;
* `__str__()` — строковое представление площадки;
* `validate_capacity()` (`@staticmethod`) — проверка корректности значения вместимости;
* `from_data()` (`@classmethod`) — создание объекта из набора данных.

### Organizer — организатор

Объект `Organizer` представляет ответственное лицо или организацию, проводящую фестиваль.

Основные атрибуты:

* `id` — уникальный идентификатор организатора;
* `name` — название организатора.

Основные методы:

* `__str__()` — строковое представление организатора;
* `from_data()` (`@classmethod`) — создание объекта из набора данных.

### Festival — фестиваль

Объект `Festival` представляет мероприятие, для которого подбирается площадка.

Основные атрибуты:

* `id` — уникальный идентификатор фестиваля;
* `name` — название фестиваля;
* `date` — дата проведения;
* `expected_attendees` — ожидаемое число посетителей;
* `organizer` — объект `Organizer`.

Основные методы:

* `__str__()` — строковое представление фестиваля с учётом организатора.

### Booking — бронирование

Объект `Booking` представляет бронирование площадки под фестиваль.

Основные атрибуты:

* `id` — уникальный идентификатор бронирования;
* `festival` — объект `Festival`;
* `venue` — объект `Venue`;
* `is_cancelled` — признак отмены бронирования.

Основные методы и свойства:

* `cancel()` — отмена бронирования (объект остаётся в коллекции);
* `booking_date` (`@property`) — дата бронирования, равная дате проведения фестиваля;
* `status` (`@property`) — текстовый статус: «активно» или «отменено»;
* `__str__()` — строковое представление бронирования с учётом его состояния.

`Booking` не наследуется от `Festival` или `Venue`: сущности не образуют иерархию
«является», поэтому вместо наследования используется композиция — бронирование хранит
ссылки на связанные объекты.

В Django-версии (ПР9–ПР10) модель `Booking` описана в `bookings/models.py`: признак
`is_cancelled` заменён полем `status` с тремя состояниями (см. раздел «Статусы бронирования
и менеджер»). Консольная версия и JSON-хранилище по-прежнему используют `is_cancelled`.

## Страницы веб-интерфейса

| Страница | URL | View-функция | Назначение |
|---|---|---|---|
| Главная | `/` | `homepage.views.index()` | описание приложения и навигация |
| Список площадок | `/venues/` | `venues.views.venues()` | площадки через ORM; поиск `?q=текст`, фильтр `?min_capacity=N` |
| Свободные площадки | `/venues/available/` | `venues.views.available()` | поиск по дате `?date=ГГГГ-ММ-ДД` и числу посетителей `?attendees=N` |
| Страница площадки | `/venues/<slug:slug>/` | `venues.views.venue_detail()` | вместимость, доступность на текущую дату, ближайшие бронирования; адрес вида `/venues/gorodskoi-park-1/` |
| Старый адрес площадки | `/venues/<int:venue_id>/` | `venues.views.venue_redirect()` | постоянное перенаправление (301) на адрес со slug |
| Административная панель | `/admin/` | `django.contrib.admin` | управление площадками, организаторами, фестивалями и бронированиями (ПР10) |
| Список бронирований | `/bookings/` | `bookings.views.bookings()` | поиск, фильтры, сортировка и пагинация (параметры ниже) |
| Статистика | `/bookings/statistics/` | `bookings.views.statistics()` | агрегаты, группировки и условие по агрегату (`aggregate()`, `annotate()`) |
| Страница бронирования | `/bookings/<int:booking_id>/` | `bookings.views.booking_detail()` | фестиваль, организатор, площадка, дата, статус |

Если площадка (по `slug`) или бронирование (по идентификатору) не найдены, представление
вызывает `get_object_or_404()`, и пользователь получает страницу 404 проекта (код ответа 404).
Ссылки на площадку в шаблонах строятся методом `Venue.get_absolute_url()`.

Параметры GET-запроса списка бронирований `/bookings/` (все необязательны, применяются
вместе):

| Параметр | Назначение |
|---|---|
| `q` | поиск по названию фестиваля, площадки и организатора (регистр не учитывается) |
| `date` | фильтр по дате фестиваля, формат `ГГГГ-ММ-ДД` |
| `venue`, `organizer` | фильтры по идентификатору площадки и организатора |
| `active=1` | только активные бронирования (`Booking.objects.active()`); отменённые и завершённые не показываются |
| `sort` | поле сортировки: `date` (по умолчанию), `venue`, `festival`, `organizer` |
| `dir=desc` | обратный порядок сортировки |
| `page` | номер страницы (по 5 бронирований на странице) |

Некорректные значения (дата не в формате `ГГГГ-ММ-ДД`, нечисловой идентификатор, неизвестное
поле сортировки, неверный номер страницы) не приводят к ошибке: пользователь видит
сообщение или значение по умолчанию. Ссылки пагинации сохраняют остальные параметры
(тег `{% querystring %}`).

### Обработка ошибки 404

Если адрес не соответствует ни одному маршруту (например, `/nonexistent/` или
`/venues/abc/`), Django вызывает обработчик 404. В режиме `DEBUG = True` вместо него
показывается техническая страница отладки со списком маршрутов, поэтому собственная
страница 404 проверяется при `DEBUG = False`.

* в корневом `venue_service/urls.py` объявлен обработчик:
  `handler404 = "homepage.views.page_not_found"` (читается только из корневого `urls.py`
  и действует для всех приложений);
* view `page_not_found(request, exception)` в `homepage/views.py` формирует страницу
  шаблоном `homepage/404.html` и возвращает ответ с кодом 404; аргумент `exception`
  обязателен, Django передаёт в него исключение, приведшее к ошибке;
* страница показывает заголовок «404 – страница не найдена», пояснение и кнопку
  «На главную», а общий вид (навигация, Bootstrap) берёт из `base.html`;
* в `settings.py` заполнен `ALLOWED_HOSTS = ["localhost", "127.0.0.1"]`: при
  `DEBUG = False` Django принимает запросы только к адресам из этого списка (иначе ответ
  400);
* несуществующие площадки и бронирования по-прежнему обрабатываются во view — собственным
  ответом со статусом 404 (`/venues/999/`, `/bookings/999/`).

Проверка: установить `DEBUG = False`, открыть `http://127.0.0.1:8000/nonexistent/` — должна
отобразиться страница проекта. После проверки в режиме разработки возвращают
`DEBUG = True`: настройка `handler404` сохраняется. При `DEBUG = False` сервер разработки
не раздаёт статические файлы проекта.

Маршрутизация двухуровневая: `venue_service/urls.py` подключает маршруты приложений
функцией `include()`, а каждое приложение описывает свои адреса в собственном `urls.py`.

Для приложений заданы пространства имён (`app_name`), а маршрутам — имена. Ссылки в
шаблонах строятся по ним тегом `{% url %}`, а не жёстко заданными адресами:

| Имя маршрута | URL |
|---|---|
| `homepage:index` | `/` |
| `venues:list` | `/venues/` |
| `venues:detail` | `/venues/<int:venue_id>/` |
| `venues:available` | `/venues/available/` |
| `bookings:list` | `/bookings/` |
| `bookings:statistics` | `/bookings/statistics/` |
| `bookings:detail` | `/bookings/<int:booking_id>/` |

## Шаблоны Django

Веб-часть использует Django Template Language. View-функции не формируют HTML: они
получают данные средствами ПР3, готовят контекст и вызывают `render()`. Функция `page()`
из ПР5 удалена и в веб-части больше не используется.

```text
View -> Context -> Template -> HTML
```

Основные приёмы:

* **базовый шаблон** `templates/base.html` — общая структура страниц, блоки
  `{% block title %}` и `{% block content %}`; дочерние шаблоны наследуют его через
  `{% extends "base.html" %}`;
* **включаемые шаблоны** `{% include %}` — навигация `templates/includes/navigation.html`,
  карточка площадки `venues/includes/venue_card.html`, статус бронирования
  `bookings/includes/booking_status.html`;
* **контекст** — view передаёт словарь, например `{"venues": venues_list}`, и шаблон
  обращается к данным по имени: `{% for venue in venues %}`;
* **циклы и условия** — `{% for %}` с `{% empty %}` для пустых коллекций, `{% if %}` для
  активного и отменённого бронирования, доступности площадки, ненайденных объектов;
* **именованные URL** — `{% url 'venues:detail' venue.id %}`;
* **фильтры** — `{{ venues|length }}`, `{{ venue.name|default:"Без названия" }}`,
  `{{ booking.booking_date|date:"d.m.Y" }}`; фильтры форматируют данные и не содержат
  бизнес-логики;
* **статические файлы** — `{% load static %}` и `{% static %}`.

Шаблоны страниц:

| Страница | Шаблон |
|---|---|
| Главная | `homepage/index.html` |
| Список площадок | `venues/venue_list.html` |
| Страница площадки | `venues/venue_detail.html` |
| Список бронирований | `bookings/booking_list.html` |
| Страница бронирования | `bookings/booking_detail.html` |
| Ошибка 404 | `homepage/404.html` |

Шаблоны уровня проекта лежат в каталоге `templates/` (он указан в `DIRS` настройки
`TEMPLATES`), шаблоны приложений — в `<приложение>/templates/<приложение>/`. Если площадка
или бронирование не найдены, во view выставляется `status=404`, а сообщение показывает
сам шаблон (`{% if venue %}` / `{% else %}`).

## Основные операции

### Используется в веб-интерфейсе (ПР5–ПР9)

* просмотр списка площадок, поиск по названию и фильтрация по вместимости (ORM: `filter()`);
* просмотр информации о площадке, проверка её доступности на текущую дату и ближайших
  бронирований (ORM: `exists()`, обратная связь `venue.bookings`);
* поиск площадок, свободных на выбранную дату (ORM: `exclude()` и `values_list()`);
* просмотр списка бронирований с поиском, фильтрами, сортировкой и пагинацией
  (ORM: `annotate()`, `values()`, `Paginator`) и информации о бронировании
  (ORM: `select_related()`);
* статистика бронирований (ORM: `aggregate()`, `annotate()`, `Count()`, `Sum()`).

### Отложено до следующих работ

Эти операции реализованы в консольной версии (ПР3). В веб-интерфейсе они появятся,
когда будут добавлены формы и POST-запросы:

* добавление площадки, организатора и фестиваля;
* поиск площадки и фестиваля по названию;
* сортировка площадок и фестивалей;
* создание и отмена бронирования.

### Работа с площадками

* добавление площадки;
* поиск площадки по названию;
* проверка вместимости;
* фильтрация площадок по вместимости;
* сортировка площадок;
* просмотр списка площадок (`find_venue_by_id()` — поиск по идентификатору для веб-страницы).

### Работа с организаторами

* добавление организатора;
* поиск организатора по названию;
* просмотр списка организаторов.

### Работа с фестивалями

* создание фестиваля с указанием организатора;
* поиск фестиваля по названию;
* фильтрация по ожидаемому числу посетителей;
* сортировка фестивалей по дате;
* просмотр списка фестивалей.

### Работа с бронированиями

* создание бронирования;
* проверка доступности площадки;
* отмена бронирования;
* просмотр списка бронирований (`find_booking_by_id()` — поиск по идентификатору
  для веб-страницы).

При создании бронирования проверяются вместимость площадки и наличие другого активного
бронирования этой площадки на ту же дату.

## Взаимодействие объектов

```text
Organizer  <-  Festival  <-  Booking  ->  Venue
```

`Festival` хранит ссылку на `Organizer` (`festival.organizer`). `Booking` хранит ссылки на
`Festival` и `Venue` (`booking.festival`, `booking.venue`), поэтому данные связанных
объектов доступны напрямую: `booking.venue.name`, `booking.festival.date`,
`booking.festival.organizer.name`.

Коллекции приложения: `List[Venue]`, `List[Organizer]`, `List[Festival]`, `List[Booking]`.

## Хранение данных

В проекте три хранилища, связанные одним набором данных:

* **JSON-файлы** (`data/*.json`) — исходные данные и хранилище консольной версии
  (`main.py`, ПР1–ПР3);
* **исходная база ПР7** (`data/festival_venue.sqlite`) — создаётся скриптом
  `db/import_json.py` из JSON; в ПР9 служит источником данных для переноса в ORM;
* **база Django** (`db.sqlite3`) — таблицы, описанные моделями и созданные миграциями; из неё
  данные читают все веб-страницы (ПР9). Файл не хранится в репозитории (он в `.gitignore`):
  после клонирования таблицы создаются командой `migrate`, а данные переносятся скриптом
  `db/import_sqlite_to_orm.py`.

Цепочка данных: `data/*.json` → `data/festival_venue.sqlite` → `db.sqlite3` → страницы.

### JSON-хранилище (ПР1–ПР3)

Данные консольной версии хранятся в JSON-файлах:

* `data/venues.json`;
* `data/organizers.json`;
* `data/festivals.json`;
* `data/bookings.json`.

При загрузке данные из JSON преобразуются в объекты `Venue`, `Organizer`, `Festival` и
`Booking`. При сохранении объекты преобразуются в данные JSON.

Связанные объекты хранятся в JSON по идентификатору. Для связи фестиваля с организатором
используется `organizer_id`, для связи бронирования с фестивалем и площадкой —
`festival_id` и `venue_id`. При загрузке идентификаторы заменяются ссылками на найденные
объекты. Записи, ссылающиеся на несуществующие объекты, пропускаются.

Пример записи бронирования:

```json
{"id": 1, "festival_id": 1, "venue_id": 1, "is_cancelled": false}
```

## База данных SQLite

Слой реляционного хранения данных появился в ПР7. SQLite хранит базу в одном файле,
`data/festival_venue.sqlite`; отдельный сервер СУБД не нужен. В ПР7 работа с базой велась
непосредственно через SQL и модуль `sqlite3`.

**В ПР9 веб-представления больше не используют этот слой:** они работают через Django ORM
(раздел «Django ORM»). Файлы `sql/schema.sql`, `sql/queries.sql`, `db/database.py`,
`db/init_db.py` и `db/import_json.py` сохранены как предыдущая реализация предметной области;
база `data/festival_venue.sqlite` используется как источник данных для переноса в ORM.

### Структура базы данных

Предметной области соответствуют четыре таблицы.

Таблица `organizers` — организаторы:

| Поле | Тип | Назначение |
|---|---|---|
| `id` | INTEGER, PRIMARY KEY | идентификатор организатора |
| `name` | TEXT, NOT NULL | название организатора |

Таблица `venues` — площадки:

| Поле | Тип | Назначение |
|---|---|---|
| `id` | INTEGER, PRIMARY KEY | идентификатор площадки |
| `name` | TEXT, NOT NULL | название площадки |
| `capacity` | INTEGER, NOT NULL, CHECK (> 0) | вместимость |

Таблица `festivals` — фестивали:

| Поле | Тип | Назначение |
|---|---|---|
| `id` | INTEGER, PRIMARY KEY | идентификатор фестиваля |
| `name` | TEXT, NOT NULL | название фестиваля |
| `date` | TEXT, NOT NULL | дата проведения в формате `ГГГГ-ММ-ДД` |
| `expected_attendees` | INTEGER, NOT NULL, CHECK (> 0) | ожидаемое число посетителей |
| `organizer_id` | INTEGER, NOT NULL, FOREIGN KEY | ссылка на `organizers.id` |

Таблица `bookings` — бронирования:

| Поле | Тип | Назначение |
|---|---|---|
| `id` | INTEGER, PRIMARY KEY | идентификатор бронирования |
| `festival_id` | INTEGER, NOT NULL, FOREIGN KEY | ссылка на `festivals.id` |
| `venue_id` | INTEGER, NOT NULL, FOREIGN KEY | ссылка на `venues.id` |
| `is_cancelled` | INTEGER, NOT NULL, DEFAULT 0, CHECK (0 или 1) | 0 — активно, 1 — отменено |

Связи между таблицами:

```text
organizers (1) ──< festivals (1) ──< bookings >── (1) venues
   organizer_id         festival_id      venue_id
```

* один организатор проводит несколько фестивалей (`festivals.organizer_id → organizers.id`);
* один фестиваль может иметь несколько бронирований (`bookings.festival_id → festivals.id`);
* одна площадка может иметь несколько бронирований (`bookings.venue_id → venues.id`).

Первичный ключ `id` однозначно идентифицирует запись и позволяет другим таблицам ссылаться
на неё. Внешние ключи не дают сохранить бронирование с несуществующим фестивалем или
площадкой. Булево значение хранится числом (SQLite не имеет отдельного логического типа).
Дата бронирования отдельно не хранится: она равна дате фестиваля и получается соединением
таблиц. Дата записывается строкой `ГГГГ-ММ-ДД`, поэтому даты можно сравнивать и сортировать
средствами SQL.

### Файлы базы данных

* `sql/schema.sql` — команды создания таблиц (`CREATE TABLE IF NOT EXISTS`, ключи,
  ограничения, индексы); повторное выполнение безопасно;
* `sql/queries.sql` — проверенные в SQLite CLI SQL-запросы проекта;
* `db/database.py` — подключение к базе: `get_connection()` включает
  `PRAGMA foreign_keys = ON` (проверка внешних ключей) и `row_factory = sqlite3.Row`
  (доступ к полям по именам), `init_schema()` выполняет `schema.sql`;
* `db/init_db.py` — создание файла базы и таблиц: `python -m db.init_db`;
* `db/import_json.py` — перенос данных из JSON в таблицы: `python -m db.import_json`;
* `data/festival_venue.sqlite` — файл базы данных.

Скрипт импорта читает JSON-файлы, вставляет записи через `executemany()` с параметрами `?`,
приводит `is_cancelled` из `true/false` к `1/0`, выполняется в одной транзакции (`commit()` при
успехе, `rollback()` при ошибке) и вставляет таблицы в порядке зависимостей: организаторы,
площадки, фестивали, бронирования — иначе внешний ключ сослался бы на отсутствующую запись.
Повторный запуск заменяет содержимое таблиц данными из JSON и не создаёт дублей.

### SQL-запросы

В `sql/queries.sql` собрано 23 запроса (минимум по заданию — 10, не менее двух каждого вида):

| Вид | Запросы | Что решают |
|---|---|---|
| Списки (`SELECT`, `ORDER BY`) | 1–3 | площадки, организаторы, фестивали |

| Агрегатные функции | 15–17 | `COUNT` активных бронирований, `MIN`/`MAX`/`AVG`/`SUM` вместимости, занятость площадки на дату |

### Получение данных из SQLite в Django-представлениях (реализация ПР7)

До перехода на ORM запросы выполняли view-функции `homepage`, `venues` и `bookings`:

```python
with closing(get_connection()) as conn:
    rows = conn.execute(FREE_VENUES_SQL, [attendees or 0, search_date.isoformat()]).fetchall()
```

* соединение создаёт `get_connection()`, результат `sqlite3.Row` доступен по именам:
  `{{ venue.name }}` в шаблоне;
* результат передаётся в шаблон через контекст, как в ПР6; шаблоны не менялись по сути:

* значения передаются параметрами `?` (параметризованные запросы). Подстановка значений

* даты из SQLite (текст) переводятся в `date` функцией `row_with_dates()`, поэтому
  фильтр шаблона `date:"d.m.Y"` продолжает работать;
* ввод пользователя проверяется до обращения к базе (число, дата `ГГГГ-ММ-ДД`).

## Django ORM

В ПР9 слой данных переведён с SQL и `sqlite3` на Django ORM. Предметная область,
страницы, шаблоны и пользовательские сценарии сохранены, изменился способ получения данных:

| Аспект | ПР7 | ПР9 |
|---|---|---|
| Описание структуры | `sql/schema.sql` | модели в `models.py` приложений |
| Изменение структуры | правка схемы вручную | миграции Django |
| Подключение | `sqlite3.connect()` | менеджер `objects` модели |
| Получение данных | запросы из `sql/queries.sql` | `filter()`, `exclude()`, `annotate()` и др. |
| Связанные данные | `JOIN` | `select_related()`, обратная связь по внешним ключам |
| Результат запроса | `sqlite3.Row` | объекты моделей, словари (`values()`) |

### Модели Django

Модели размещены в `models.py` приложений. Их не следует путать с пакетом `models/`
(классы консольной версии, ПР3): это разные сущности с одинаковыми названиями.

| Модель | Приложение | Поля |
|---|---|---|
| `Organizer` | `festivals` | `name` |
| `Venue` | `venues` | `name`, `capacity`, `is_large` (вычисляется базой), `slug` |
| `Festival` | `festivals` | `name`, `date`, `expected_attendees`, `organizer` (внешний ключ) |
| `Booking` | `bookings` | `festival` и `venue` (внешние ключи), `status` (`active`, `cancelled`, `completed`) |

Первичный ключ `id` Django создаёт автоматически. Для полей выбраны типы по назначению:
`CharField` (названия), `PositiveIntegerField` (вместимость, число посетителей), `DateField`
(дата фестиваля, в запросах сравнивается с объектом `date`), `CharField` с `choices`
(`Booking.status`, по умолчанию «активно»), `SlugField` (адрес площадки), `GeneratedField`
(`Venue.is_large`). Ограничения `CheckConstraint` не допускают нулевую вместимость и ноль
посетителей. Все модели имеют `__str__()`, сортировку по умолчанию и русские названия
(`verbose_name`); модели зарегистрированы в админ-панели.

Методы моделей: `Venue.is_suitable_for()`, `Venue.is_available_on(day)` (площадку блокирует
только активное бронирование), `Venue.get_absolute_url()`, `Booking.cancel()` и
`Booking.complete()` (сохраняют только поле `status`), `Booking.clean()` (проверка правила
«одна площадка — одно активное бронирование на дату»), свойство `Booking.booking_date`
(дата фестиваля).

### Связи между моделями

Все связи — «многие к одному» (`ForeignKey`):

| Поле | Ссылается на | `on_delete` | `related_name` |
|---|---|---|---|
| `Festival.organizer` | `Organizer` | `PROTECT` | `festivals` |
| `Booking.festival` | `Festival` | `PROTECT` | `bookings` |
| `Booking.venue` | `Venue` | `PROTECT` | `bookings` |

`PROTECT` запрещает удалять организатора, фестиваль и площадку, на которые ссылаются другие
записи: история бронирований не теряется (при попытке возникает `ProtectedError`).
`related_name` задаёт обратный доступ: `venue.bookings.all()`, `festival.bookings.all()`,
`organizer.festivals.all()`. В базе Django хранятся столбцы `venue_id`, `festival_id`,
`organizer_id`; в коде доступны и объект (`booking.venue`), и идентификатор
(`booking.venue_id`). Дата бронирования, как и в ПР7, берётся у фестиваля. Правило «одна
площадка не может иметь два активных бронирования на одну дату» проверяется в
`Booking.clean()` (его вызывают формы административной панели), в массовом действии
«Вернуть в активные» и во view поиска свободных площадок; на уровне базы данных это
ограничение не задано, поэтому при создании записей через `create()` или `save()` без
`full_clean()` оно не проверяется.

### Миграции

Структура базы управляется миграциями, они лежат в `<приложение>/migrations/` и хранятся в Git:

```bash
python manage.py makemigrations        # создать файлы миграций по моделям
python manage.py sqlmigrate venues 0001  # посмотреть SQL миграции
python manage.py migrate               # применить миграции к базе
python manage.py showmigrations        # состояние миграций ([X] — применена)
python manage.py makemigrations --check  # проверить, что все изменения моделей учтены
```

`makemigrations` формирует файлы миграций, `migrate` применяет их к базе. Изменять таблицы
Django вручную командами SQL не следует.

### Стратегия перехода и перенос данных

Выбран вариант «таблицы, управляемые Django, и перенос данных»: исходная база ПР7
(`data/festival_venue.sqlite`) не изменяется, а Django работает с отдельной базой
`db.sqlite3` (настройка `DATABASES`). Перенос выполняют два скрипта в каталоге `db/`:

```bash
python manage.py migrate                 # создать таблицы Django
python db/inspect_source_db.py           # проверить исходную базу (только чтение)
python db/import_sqlite_to_orm.py        # перенести данные средствами ORM
```

* `db/inspect_source_db.py` выводит таблицы, столбцы и число записей и проверяет целостность:
  ссылки на существующие записи, значения `is_cancelled`, формат дат;
* `db/import_sqlite_to_orm.py` читает исходную базу только для чтения и создаёт записи
  методом `update_or_create()` с сохранением идентификаторов; порядок: организаторы, площадки,
  фестивали, бронирования; строки дат превращаются в `date`, `0/1` — в `bool`; всё выполняется
  в одной транзакции (`transaction.atomic()`); повторный запуск не создаёт дублей и не удаляет
  лишние записи.

Перед переносом удобно сделать резервную копию исходной базы
(`cp data/festival_venue.sqlite data/festival_venue_backup.sqlite`); копии
`data/*_backup.sqlite` исключены из Git. После переноса в базе 3 организатора, 4 площадки,
7 фестивалей и 8 бронирований — столько же, сколько в исходной базе.

### Операции ORM в Django shell

```bash
python manage.py shell
```

```python
from venues.models import Venue
from bookings.models import Booking

venue = Venue.objects.create(name="Тестовая площадка", capacity=100)  # Create
Venue.objects.filter(capacity__gte=100)                                # Read
venue.capacity = 150
venue.save()                                                           # Update
venue.delete()                                                         # Delete

booking = Booking.objects.select_related("festival", "venue").first()
booking.venue.name, booking.festival.organizer.name                    # прямая связь
booking.venue.bookings.count()                                         # обратная связь
```

Изменение атрибута объекта само по себе не сохраняет данные в базе: для этого нужен `save()`.
Метод `get()` ожидает ровно одну запись (иначе `DoesNotExist` или `MultipleObjectsReturned`),
`filter()` возвращает `QuerySet`, в том числе пустой.

### ORM-запросы проекта

В проекте реализовано более 15 различных ORM-выражений, все они используются страницами:

| Вид | Выражение | Где используется |
|---|---|---|
| Получение данных | `Venue.objects.all()` (сортировка по `Meta.ordering`) | список площадок |
| | `get_object_or_404(Venue, pk=...)` | страница площадки |
| | `get_object_or_404(Booking.objects.select_related(...), pk=...)` | страница бронирования |
| Фильтрация | `filter(capacity__gte=N)` | фильтр площадок по вместимости |
| | `Booking.objects.active()`, `filter(venue_id=...)`, `filter(festival__date=...)` (несколько условий) | список бронирований |
| | `filter(festival__organizer_id=...)` (поле связанной модели) | список бронирований |
| | `exclude(pk__in=...)` | поиск свободных площадок |
| | `filter(date__gte=today)[:3]` | ближайшие фестивали на главной |
| Поиск | `search_text(..., ["name"], q)` (одно текстовое поле) | список площадок |
| | `search_text(..., ["festival__name", "venue__name", "festival__organizer__name"], q)` (несколько полей, `Q` с `OR`) | список бронирований |
| Сортировка | `order_by("capacity", "name")` (несколько полей) | площадки с фильтром |
| | `order_by(SORT_FIELDS[sort], "pk")`, в том числе по полям связанных моделей | список бронирований |
| Связи | `select_related("festival__organizer", "venue")` | страница бронирования |
| | `select_related("organizer")` | ближайшие фестивали |
| | `venue.bookings.select_related("festival").filter(...)` (обратная связь) | страница площадки |
| | `annotate(festival_name=F("festival__name"), ...)` и `values(...)` | список бронирований |
| Агрегирование | `Venue.objects.aggregate(Count, Min, Max, Avg, Sum)`; `count()` | статистика, главная |
| | `annotate(Count("bookings", filter=Q(bookings__status="active")))` | бронирования по площадкам |
| | `aggregate(Count("id", filter=Q(status=...)))` для трёх статусов | статистика по статусам |
| Менеджер | `Booking.objects.active()`, `cancelled()`, `completed()`, `for_date(day)` и их цепочки | страницы, доступность, администрирование |
| | `annotate(Count("festivals"), Sum("festivals__expected_attendees"))` | фестивали по организаторам |
| | `filter(bookings_count__gt=2)` по агрегату (аналог `HAVING`) | «часто бронируемые» площадки |
| Прочее | `values_list("venue_id", flat=True)`; `exists()` | свободные площадки, доступность |
| Пагинация | `Paginator(bookings, 5).get_page(...)` | список бронирований |

Особенности реализации:

* порядок записей по умолчанию задан в `Meta.ordering` моделей;
* поле сортировки выбирается только из словаря `SORT_FIELDS`, произвольное значение из URL в
  `order_by()` не передаётся;
* статистика строится от модели `Venue`, а условие по статусу задано внутри
  `Count(..., filter=Q(...))`: площадки без активных бронирований остаются в результате со
  значением 0, отменённые и завершённые бронирования не учитываются;
* поиск по тексту (`venue_service/search.py`): встроенный `icontains` и функция `LOWER` в SQLite
  различают регистр только у латиницы, поэтому для кириллицы зарегистрирована функция
  `UNICODE_LOWER`; символы `%` и `_` в запросе трактуются как обычный текст;
* параметры запроса проверяются в `venue_service/params.py` до обращения к базе;
* для списка бронирований используются `annotate()` с `F()` и `values()`: возвращаются
  словари только с нужными полями, поэтому `select_related()` не требуется; для карточки,
  где нужны объекты целиком, применяется `select_related()` (один запрос вместо четырёх).

  тесты и консольная версия работают без неё;
* `INTERNAL_IPS = ["127.0.0.1"]`, поэтому сайт нужно открывать по адресу
  `http://127.0.0.1:8000/` (не `localhost`), иначе панель не появится;
* маршруты панели подключены по адресу `/__debug__/`.

После запуска `python manage.py runserver` панель «DJDT» появляется справа на страницах;
вкладка **SQL** показывает число запросов, их текст и время выполнения. Например, страница
`/bookings/1/` выполняет один запрос с соединением таблиц бронирований, фестивалей,
организаторов и площадок (`select_related()`), а список `/bookings/` выбирает только нужные
столбцы (`annotate()` и `values()`) и отдельным запросом считает записи для пагинации.
Тот же SQL можно получить в shell: `print(queryset.query)`.

### Статусы бронирования и менеджер (ПР10)

Булево поле `is_cancelled` заменено полем `Booking.status` на основе `TextChoices`:

| Код в базе | Название | Блокирует площадку |
|---|---|---|
| `active` | Активно | да |
| `cancelled` | Отменено | нет |
| `completed` | Завершено | нет |

Миграции `bookings`: `0002_booking_status` (поле `status`), `0003_migrate_booking_statuses`
(перенос данных: `is_cancelled=True` → `cancelled`, остальные → `active`, обратная операция
тоже описана), `0004_remove_booking_is_cancelled` (удаление старого поля),
`0005_booking_status_help_text`. Статус `completed` по дате автоматически не назначается:
его выставляют вручную (метод `complete()` или действие в админ-панели).

`BookingQuerySet` и `BookingManager` (`Booking.objects`) содержат методы `active()`,
`cancelled()`, `completed()` и `for_date(day)` (по `festival__date`); их можно соединять в
цепочку и вызывать у обратной связи: `venue.bookings.active()`. Метод `all()` по-прежнему
возвращает все записи, включая отменённые, — история сохраняется. Менеджер используют списки,
поиск свободных площадок, статистика и главная страница.

### Вычисляемое поле, slug и get_absolute_url (ПР10)

* `Venue.is_large` — `GeneratedField`: значение «вместимость не менее 3000» вычисляет сама
  база данных и хранит в таблице (`db_persist=True`), в SQLite это столбец
  `GENERATED ALWAYS AS (...) STORED`. Поле нельзя изменить вручную, при изменении
  `capacity` оно пересчитывается; по нему можно фильтровать (`filter(is_large=True)`).
* `Venue.slug` — транслитерация названия (библиотека `Unidecode`) и идентификатор, например
  `gorodskoi-park-1`. Формируется в `Venue.save()` один раз и при переименовании не меняется;
  уникален (`unique=True`) и не редактируется в формах. Миграции `venues`:
  `0004_venue_slug` (поле), `0005_populate_venue_slugs` (заполнение существующих площадок),
  `0006_venue_slug_unique` (ограничение уникальности).
* `Venue.get_absolute_url()` возвращает `/venues/<slug>/` через `reverse("venues:detail")`;
  метод используют шаблоны и ссылка «Смотреть на сайте» в админ-панели. Старые адреса
  `/venues/<id>/` перенаправляются на новые (код 301).
* Миграции `venues`: `0002_venue_capacity_help_text` (подсказка к полю вместимости),
  `0003_venue_is_large`.

### Контекстный процессор (ПР10)

Функция `homepage.context_processors.site_context` зарегистрирована в `TEMPLATES` и передаёт
во все шаблоны `site_name` («Festival Venue Service») и `venues_count` (число площадок,
`Venue.objects.count()`). Они используются в `base.html` (заголовок по умолчанию, логотип,
подвал) и в навигации («Площадки (N)»). Процессор выполняет один дополнительный запрос
`COUNT` при формировании каждой страницы, поэтому в тестах, считающих запросы, он учтён.

## Административная панель Django (ПР10)

Панель доступна по адресу `/admin/`. Для входа нужен суперпользователь:

```bash
python manage.py migrate
python manage.py createsuperuser
```

Названия приложений заданы в `AppConfig.verbose_name` («Площадки», «Организаторы и
фестивали», «Бронирования»), `LANGUAGE_CODE = "ru-RU"`, у моделей и полей заданы
`verbose_name`, у вместимости площадки и статуса бронирования — `help_text`.

| Модель | Настройки `ModelAdmin` |
|---|---|
| `Venue` | столбцы: id, название, вместимость, «Большая площадка», активных бронирований (аннотация `Count`), ссылка на сайт; вместимость правится в списке (`list_editable`); поиск по названию; фильтр по `is_large`; `id`, `slug`, `is_large` только для чтения; `view_on_site`; inline «Бронирования площадки» (статус можно менять, добавлять записи нельзя) |
| `Organizer` | столбцы: id, название, число фестивалей (аннотация); поиск; inline «Фестивали организатора» |
| `Festival` | поиск по названию фестиваля и организатора; фильтры по дате и организатору; навигация по датам (`date_hierarchy`); автопоиск организатора; inline «Бронирования фестиваля» |
| `Booking` | столбцы: id, фестиваль, площадка, вместимость и дата (методы-столбцы), статус; поиск по `festival__name`, `venue__name`, `festival__organizer__name`; фильтры по статусу, дате и площадке; `list_select_related`; автопоиск фестиваля и площадки; действия: отменить, отметить завершёнными, вернуть в активные |

Действие «Вернуть в активные» не возвращает бронирование, если площадка на эту дату уже
занята другим активным бронированием, и сообщает о пропуске: настройка админ-панели не
заменяет правила предметной области. Форма добавления бронирования проверяет то же правило
в `Booking.clean()`.

Число SQL-запросов (панель Django Debug Toolbar): страница списка бронирований выполняет
5 запросов, страница бронирования — 2 (один с `select_related()` и `COUNT` процессора).
`list_select_related` у `BookingAdmin` задаёт состав присоединяемых таблиц: если в
`list_display` есть столбцы-внешние ключи, `ChangeList` присоединяет их сам, а для
столбцов-методов (`venue_capacity`, `festival_date`) без этого параметра возникает проблема
N+1 (в тесте — рост числа запросов на два на каждую строку списка).

## Назначение модулей

### `main.py`

Консольная версия приложения (сохранена с ПР3). Отвечает за запуск приложения, отображение меню, получение данных
от пользователя и организацию пользовательских сценариев (в том числе `create_new_booking()`).

### `venue_service/`

Пакет конфигурации Django-проекта:

* `settings.py` — настройки проекта (русская локаль, часовой пояс Europe/Moscow, база
  `db.sqlite3`);
* `urls.py` — маршрутизация верхнего уровня;
* `params.py` — разбор и проверка параметров GET-запроса (число, дата);
* `search.py` — поиск по текстовым полям без учёта регистра для кириллицы;
* `asgi.py`, `wsgi.py` — точки взаимодействия с сервером.

### `homepage/`

Django-приложение главной страницы:

* `views.py` — view-функция `index()` (сводка и ближайшие фестивали через ORM) и
  обработчик ошибки 404 `page_not_found()`;
* `urls.py` — маршрут главной страницы (`app_name = "homepage"`);
* `templates/homepage/index.html` — шаблон главной страницы;
* `templates/homepage/404.html` — страница ошибки 404;
* `static/homepage/` — общие статические файлы проекта: CSS, JavaScript и логотип.

Статические файлы размещены здесь, потому что главная страница задаёт общий вид всех
остальных страниц.

### `templates/`

Шаблоны уровня проекта: базовый шаблон `base.html` (структура страницы, блоки, подключение
CSS, JavaScript и логотипа, подвал) и включаемый шаблон навигации
`includes/navigation.html`.

### `venues/`

Django-приложение площадок:

* `views.py` — view-функции `venues()`, `venue_detail()` и `available()`: получают данные
  через ORM, готовят контекст и вызывают `render()`;
* `urls.py` — маршруты приложения (`app_name = "venues"`);
* `templates/venues/` — шаблоны списка, страницы площадки и поиска свободных площадок,
  включаемая карточка;
* `models.py` — модель `Venue` (`is_large`, `slug`, `get_absolute_url()`);
* `admin.py` — `VenueAdmin` и inline бронирований.

### `festivals/`

Django-приложение организаторов и фестивалей: `models.py` (модели `Organizer` и `Festival`),
`admin.py` (`OrganizerAdmin`, `FestivalAdmin`, inline), `migrations/`. Страниц у приложения
пока нет.

### `bookings/`

Django-приложение бронирований:

* `views.py` — view-функции `bookings()` (поиск, фильтры, сортировка, пагинация),
  `booking_detail()` и `statistics()` (агрегаты и группировки через ORM);
* `urls.py` — маршруты приложения (`app_name = "bookings"`);
* `templates/bookings/` — шаблоны списка, страницы бронирования и статистики, включаемый
  статус;
* `models.py` — модель `Booking`, `BookingQuerySet` и `BookingManager`;
* `admin.py` — `BookingAdmin` с поиском, фильтрами и массовыми действиями.

### `models/`

Классы предметной области и функции работы с ними (пакет ПР3):

* `venues.py`, `organizers.py`, `festivals.py` — классы `Venue`, `Organizer`, `Festival` и
  функции работы с коллекциями: добавление, поиск, фильтрация, сортировка, вывод;
* `schedule.py` — класс `Booking` и функции `is_venue_available()`, `create_booking()`,
  `cancel_booking()`, `check_venue_suitability()`, `find_booking_by_id()`,
  `show_bookings()`.

Пакет `models/` не следует путать с файлами `models.py` Django-приложений: в них описаны
модели Django (ПР9), а пакет `models/` сохранён для консольной версии.

### `db/` и `sql/`

Слой базы данных SQLite (ПР7): `db/database.py` (подключение), `db/init_db.py` (создание
таблиц), `db/import_json.py` (перенос данных из JSON), `sql/schema.sql` (схема),
`sql/queries.sql` (запросы) — предыдущая реализация, подробнее в разделе «База данных SQLite».
Перенос данных в ORM (ПР9): `db/inspect_source_db.py` (проверка исходной базы) и
`db/import_sqlite_to_orm.py` (перенос в таблицы Django).

### `storage.py`

Отвечает за загрузку и сохранение JSON-данных консольной версии. Выполняет преобразование:

* JSON → объекты Python;
* объекты Python → JSON.

### `utils.py`

Содержит вспомогательные функции:

* `input_int()` — безопасный ввод целого числа;
* `input_date()` — безопасный ввод даты;
* `describe_function()` — вывод сигнатуры и описания функции (интроспекция).

### `tests/`

Содержит автоматизированные тесты проекта: тесты классов и хранилища (ПР3), тесты моделей
Django и переноса данных (`test_models.py`, `test_transfer_to_orm.py`), тесты ПР10
(`test_booking_statuses.py` — статусы, менеджер и миграция данных, `test_venue_slug.py` —
slug, `GeneratedField` и контекстный процессор, `test_admin.py` — административная панель)
и тесты веб-слоя: `test_urls.py` (именованные маршруты), `test_404.py` (обработчик ошибки 404), `test_homepage.py`, `test_venue_pages.py`,
`test_booking_pages.py`, `test_free_venues.py`, `test_statistics.py` (шаблоны, контекст,
коды ответов, данные из ORM), `test_booking_filters.py` (поиск, фильтры, сортировка и
пагинация списка бронирований), `test_static.py` (статические файлы),
`test_no_html_in_views.py` (в view-функциях нет HTML); слоя базы данных: `test_db_schema.py`
(таблицы, ключи, ограничения), `test_import_json.py` (перенос данных), `test_sql_queries.py`
(файл запросов), `test_no_fstring_sql.py` (SQL без f-строк). Тесты работают через
`pytest-django` на временной тестовой базе, которую создают миграции проекта; страницы
проверяются через `django.test.Client`.

## Запуск приложения

Установка зависимостей (рекомендуется в виртуальном окружении):

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

Перед первым запуском веб-версии создать таблицы (миграции Django) и перенести в них данные
из исходной базы:

```bash
python manage.py migrate
python db/import_sqlite_to_orm.py
```

Файл базы Django `db.sqlite3` в репозитории не хранится. Исходная база ПР7
`data/festival_venue.sqlite` лежит в репозитории; чтобы создать её заново или обновить
после изменения JSON-файлов (затем повторить перенос в ORM):

```bash
python -m db.init_db      # создать файл базы и таблицы (sql/schema.sql)
python -m db.import_json  # перенести данные из data/*.json в таблицы
python db/import_sqlite_to_orm.py  # обновить данные в базе Django
```

Проверка запросов ПР7 в SQLite CLI:

```bash
sqlite3 data/festival_venue.sqlite
sqlite> .read sql/queries.sql
```

Веб-версия (Django):

```bash
python manage.py runserver
```

После запуска открыть в браузере адрес:

```text
http://127.0.0.1:8000/
```

Для оформления страниц Bootstrap загружается через CDN, поэтому нужен доступ в интернет.
Консольная версия читает `data/*.json` относительными путями и запускается из корня проекта.

Консольная версия (сохранена):

```bash
python main.py
```

После запуска отображается главное меню.

## Тестирование

Для запуска автоматизированных тестов выполнить:

```bash
pytest
```

Настройки `pytest` (подробный вывод `-v`) заданы в `setup.cfg`.

Тесты проверяют:

* создание и работу объектов `Venue`, `Organizer`, `Festival` и `Booking`;
* методы и свойства классов;
* операции с площадками, организаторами и фестивалями;
* создание и отмену бронирований;
* связь бронирования с фестивалем и площадкой;
* правила доступности площадки;
* загрузку и сохранение данных в JSON, восстановление связей между объектами;

## Проверка качества кода

Для проверки соответствия кода требованиям PEP 8 используется `flake8`.

Команда проверки:

```bash
flake8 .
```

Форматирование проверяется командой `black --check .`, системная проверка Django —
`python manage.py check`.

## Зависимости

Состав зависимостей в `requirements.txt`:

* `Django==5.2.*` — веб-фреймворк;
* `django-debug-toolbar` — панель отладки с просмотром SQL-запросов (используется при
  `DEBUG = True`);
* `Unidecode` — транслитерация названий площадок при формировании `slug`;
* `pytest` и `pytest-django` — автоматизированные тесты (в том числе с базой Django);
* `flake8` — проверка качества кода;
* `black` — форматирование кода.

Модуль `sqlite3` входит в стандартную библиотеку Python, а SQLite CLI (`sqlite3`) обычно
уже установлен в системе; отдельных зависимостей для базы данных не требуется.
